# Курсовая работа: совместные подборки котиков в Kittygram

> Статус документа: проектное решение для творческого задания. Описанная ниже
> функциональность **ещё не реализована**. Существующая база проекта отмечена
> отдельно, чтобы в итоговой курсовой не выдать планируемое за готовое.

## Тема, цель и задачи работы

**Тема:** проектирование и реализация REST API для совместных подборок котиков
> в веб-сервисе Kittygram.

**Цель:** расширить Kittygram механизмом совместных подборок, в которых
> несколько пользователей могут просматривать и, в зависимости от роли,
> редактировать состав котиков.

**Объект исследования:** API веб-сервиса для публикации и управления данными о
> котиках.

**Предмет исследования:** модели данных, REST API, разграничение прав доступа,
> валидация и тестирование совместной работы пользователей с подборками.

**Задачи:**

1. Проанализировать текущий API Kittygram и определить требования к новой
   механике.
2. Спроектировать модели подборки и участия пользователя в подборке.
3. Спроектировать API-контракт, роли, ограничения и сценарии ошибок.
4. Реализовать API и автоматические тесты.
5. Подготовить документацию API, Postman-коллекцию, диаграммы и доказательства
   развёртывания.

**Используемые технологии:** Python, Django, Django REST Framework, Djoser,
> Simple JWT, django-filter, PostgreSQL, Docker Compose, Nginx и React.

# Глава 1. Аналитика и постановка задачи

## 1.1. Текущее состояние Kittygram

В проекте уже реализованы авторизация по JWT, CRUD API котиков, изображения
> котиков, достижения, владение котом, фильтрация, поиск, сортировка и
> постраничный вывод. Изменять котика может только его владелец. Базовая
> инфраструктура содержит Docker Compose с PostgreSQL, Nginx и CI-конфигурацию.

Новая механика не дублирует достижения и не изменяет базовую модель `Cat`.
> Она использует существующих пользователей и котиков как связанные сущности.

### Граница готового решения

| Область | Состояние на момент аудита |
|---|---|
| `cats.Cat`, пользователь-владелец и достижения | Уже реализовано |
| JWT, регистрация и API текущего пользователя | Уже реализовано |
| Пагинация и фильтрация списка котиков | Уже реализовано |
| Docker Compose, PostgreSQL-конфигурация, Nginx | Реализовано и локально проверено: сборка, миграции и защищённый API через Nginx |
| Совместные подборки и роли участников | Реализовано в исходном коде; выполнение тестов локально ещё не подтверждено |
| Документация нового API и Postman | Реализовано; диаграммы остаются в плане |
| Успешный запуск тестов в текущем рабочем окружении | Подтверждён: `manage.py check`, проверка миграций и 38 тестов `cats`/`collaborations` выполнены в Docker Compose с PostgreSQL |
| Работающий внешний деплой | Не подтверждён |

## 1.2. Описание идеи и пользовательский сценарий

Пользователь создаёт тематическую подборку, например «Коты из приютов,
> которым нужна семья», и приглашает знакомых к совместной работе. Владелец
> управляет участниками и их ролями. Редактор может добавить в подборку
> собственного кота или удалить ранее добавленного. Читатель видит подборку и
> её состав, но ничего не изменяет.

Механика полезна, когда подборку ведут несколько волонтёров, членов семьи или
> администраторов сообщества. Вместо передачи ссылок и единственного владельца
> создаётся контролируемое совместное пространство с понятной ответственностью
> каждого участника.

## 1.3. Функциональные требования

1. Авторизованный пользователь может создать подборку.
2. Участник видит только те подборки, в которых состоит.
3. Владелец может получить список участников, пригласить пользователя,
   изменить роль редактора или читателя и удалить участника.
4. Владелец и редактор могут добавлять в подборку только собственных котиков
   и удалять котиков из подборки.
5. Читатель может просматривать подборку и участников, но не изменять их.
6. Список доступных пользователю подборок поддерживает поиск, фильтрацию по
   роли и пагинацию.
7. Любой авторизованный пользователь может предложить собственного котика в
   подборку; котик не добавляется до решения владельца или редактора.
8. Владелец или редактор может одобрить либо отклонить ожидающую заявку.
9. API возвращает предсказуемые коды статуса и сообщения о нарушении правил.

## 1.4. Нефункциональные требования и ограничения

- Все новые маршруты доступны только авторизованному пользователю.
- Мутации выполняются атомарно: создание подборки создаёт и запись владельца в
  составе участников.
- Секреты не хранятся в коде; используется существующий `.env.example`.
- Контракт сохраняет JSON и принципы существующего DRF API.
- В этой итерации нет публичного каталога, уведомлений, заявок на вступление и
  передачи владения. Это намеренное ограничение объёма работы.

# Глава 2. Проектирование

## 2.1. Модель данных

### Новые модели

| Модель | Назначение | Ключевые поля | Связи | Ограничения |
|---|---|---|---|---|
| `Collection` | Тематическая подборка котиков | `title`, `description`, `owner`, `cats`, `created_at`, `updated_at` | `owner` -> `User` (FK); `cats` <-> `Cat` (M2M); `members` -> `CollectionMember` | `title` уникален в пределах одного владельца; длина 3-80 символов |
| `CollectionMember` | Участие пользователя и его роль | `collection`, `user`, `role`, `created_at` | `collection` -> `Collection` (FK); `user` -> `User` (FK) | уникальная пара `collection + user`; роль: `owner`, `editor` или `viewer` |
| `CollectionCatProposal` | Заявка на добавление котика в подборку | `collection`, `cat`, `proposer`, `status`, `reviewed_by`, `reviewed_at` | `collection` -> `Collection` (FK); `cat` -> `Cat` (FK); пользователи предлагают и рассматривают заявку | уникальная пара `collection + cat`; статус: `pending`, `approved`, `rejected` |

### Связи сущностей

```text
User 1 --- * Collection            (владелец)
User 1 --- * CollectionMember * --- 1 Collection
Collection * --- * Cat             (состав подборки)
User 1 --- * Cat                   (существующий владелец кота)
User 1 --- * CollectionCatProposal * --- 1 Collection
Cat 1 --- * CollectionCatProposal  (котик в заявке)
```

При создании `Collection` в одной транзакции создаётся `CollectionMember` для
> автора с ролью `owner`. Поле `Collection.owner` остаётся источником истины о
> владельце; соответствующая запись участника нужна для единообразного списка
> участников и ролей.

## 2.2. Роли и права доступа

| Роль | Чтение подборки и участников | Изменение подборки | Управление участниками | Добавление/удаление котов | Рассмотрение заявок | Удаление подборки |
|---|---:|---:|---:|---:|---:|---:|
| Владелец | Да | Да | Да | Да | Да | Да |
| Редактор | Да | Нет | Нет | Да | Да | Нет |
| Читатель | Да | Нет | Нет | Нет | Нет | Нет |
| Пользователь вне подборки | Нет | Нет | Нет | Нет | Может создать заявку на собственного котика | Нет |

Для добавления котика недостаточно роли владельца или редактора: котик также
> должен принадлежать пользователю, который выполняет запрос. Это не позволяет
> одному участнику включать чужих питомцев без согласия владельца.

## 2.3. Бизнес-правила и валидации

| № | Правило | Где проверяется | Ответ при нарушении | Пример |
|---:|---|---|---|---|
| 1 | Нельзя добавить пользователя в одну подборку повторно | Сериализатор приглашения и ограничение БД `UniqueConstraint` | `400 Bad Request` | Приглашение уже существующего редактора |
| 2 | Нельзя удалить владельца, понизить его роль или изменить её | Action управления участником | `400 Bad Request` | `PATCH` роли владельца на `viewer` |
| 3 | Добавлять в подборку можно только своего кота | Action добавления кота | `403 Forbidden` | Редактор передаёт `cat_id` другого пользователя |
| 4 | Один котик не может повторно находиться в одной подборке | Action добавления кота и M2M-проверка | `400 Bad Request` | Повторный `POST` с тем же `cat_id` |
| 5 | Изменять состав могут только владелец и редактор | Permission-класс/action | `403 Forbidden` | Читатель пытается добавить кота |
| 6 | Заголовок подборки уникален у владельца | Сериализатор и ограничение БД | `400 Bad Request` | Вторая «Коты из приюта» у одного автора |

## 2.4. Варианты использования (Use Case)

Акторы: авторизованный пользователь, владелец подборки, редактор, читатель.

1. Пользователь создаёт подборку и автоматически становится владельцем.
2. Владелец приглашает пользователя как редактора или читателя.
3. Владелец меняет роль участника или исключает его.
4. Владелец или редактор добавляет собственного кота в подборку.
5. Владелец или редактор удаляет кота из подборки.
6. Читатель просматривает подборку и список участников.
7. Участник ищет свои подборки и отфильтровывает их по роли.

В итоговой работе этот раздел будет преобразован в диаграмму Use Case с
> указанными актёрами и сценариями.

## 2.5. API-контракт

**Базовый URL:** `/api/`.

Новый роутер зарегистрирует ресурс `collections`. Все ответы используют JSON и
> требуют `Authorization: Bearer <access_token>`. Текущие маршруты `/api/cats/`,
> `/api/users/`, `/api/achievements/` и JWT-маршруты сохраняются без изменения.

### Таблица API-эндпоинтов

| № | URL | Метод | Назначение | Права доступа | Тело запроса | Успешный код | Ошибки и валидация |
|---:|---|---|---|---|---|---:|---|
| 1 | `/api/collections/` | `GET` | Список подборок текущего пользователя | Участник | — | 200 | 401 без токена |
| 2 | `/api/collections/` | `POST` | Создать подборку и членство владельца | Авторизованный | `title`, `description` | 201 | 400: повтор названия у владельца; 401 |
| 3 | `/api/collections/{id}/` | `GET` | Получить подборку и её состав | Участник подборки | — | 200 | 403: не участник; 404 |
| 4 | `/api/collections/{id}/` | `PATCH` | Изменить название или описание | Владелец | `title` и/или `description` | 200 | 400: невалидный/повторный заголовок; 403 |
| 5 | `/api/collections/{id}/` | `DELETE` | Удалить подборку вместе с составом и участниками | Владелец | — | 204 | 403; 404 |
| 6 | `/api/collections/{id}/members/` | `GET` | Получить участников и их роли | Участник подборки | — | 200 | 403; 404 |
| 7 | `/api/collections/{id}/members/` | `POST` | Пригласить редактора или читателя | Владелец | `user_id`, `role` | 201 | 400: уже участник, неверный пользователь или роль `owner`; 403; 404: подборка |
| 8 | `/api/collections/{id}/members/{user_id}/` | `PATCH` | Изменить роль редактора или читателя | Владелец | `role` | 200 | 400: попытка изменить владельца; 403; 404 |
| 9 | `/api/collections/{id}/members/{user_id}/` | `DELETE` | Исключить участника | Владелец | — | 204 | 400: попытка удалить владельца; 403; 404 |
| 10 | `/api/collections/{id}/cats/` | `POST` | Добавить собственного котика в подборку | Владелец или редактор | `cat_id` | 201 | 400: дубликат; 403: читатель или чужой кот; 404 |
| 11 | `/api/collections/{id}/cats/{cat_id}/` | `DELETE` | Удалить котика из подборки | Владелец или редактор | — | 204 | 403; 404: котика нет в подборке |
| 12 | `/api/collections/{id}/proposals/` | `POST` | Предложить собственного котика | Любой авторизованный | `cat_id` | 201 | 400: дубликат/кот уже в подборке; 403: чужой кот; 404 |
| 13 | `/api/collections/{id}/proposals/` | `GET` | Получить заявки на добавление котиков | Владелец или редактор | — | 200 | 403; 404 |
| 14 | `/api/collections/{id}/proposals/{proposal_id}/approve/` | `POST` | Одобрить ожидающую заявку и добавить котика | Владелец или редактор | — | 200 | 400: заявка уже рассмотрена; 403; 404 |
| 15 | `/api/collections/{id}/proposals/{proposal_id}/reject/` | `POST` | Отклонить ожидающую заявку | Владелец или редактор | — | 200 | 400: заявка уже рассмотрена; 403; 404 |

### Фильтрация и пагинация

Ресурс `GET /api/collections/` использует уже настроенную в проекте
> `PageNumberPagination` с размером страницы 10. Для него добавляются:

| Параметр | Назначение | Пример |
|---|---|---|
| `search` | Поиск по `title` и `description` | `/api/collections/?search=приют` |
| `role` | Отбор подборок, где у пользователя определённая роль | `/api/collections/?role=editor` |
| `page` | Номер страницы | `/api/collections/?page=2` |

## 2.6. Примеры JSON

### Создание подборки

`POST /api/collections/`

```json
{
  "title": "Коты из приютов",
  "description": "Подборка питомцев, которым нужен дом"
}
```

Ответ `201 Created`:

```json
{
  "id": 12,
  "title": "Коты из приютов",
  "description": "Подборка питомцев, которым нужен дом",
  "owner": 4,
  "my_role": "owner",
  "cats": [],
  "members_count": 1,
  "created_at": "2026-10-28T14:00:00+03:00",
  "updated_at": "2026-10-28T14:00:00+03:00"
}
```

### Приглашение участника

`POST /api/collections/12/members/`

```json
{
  "user_id": 7,
  "role": "editor"
}
```

Ответ `201 Created`:

```json
{
  "user": 7,
  "username": "volunteer_anna",
  "role": "editor",
  "created_at": "2026-10-28T14:05:00+03:00"
}
```

### Добавление котика

`POST /api/collections/12/cats/`

```json
{
  "cat_id": 31
}
```

Ответ `201 Created`:

```json
{
  "id": 31,
  "name": "Мурка",
  "color": "#FFFFFF"
}
```

### Пример ошибки валидации

Повторное добавление котика:

```json
{
  "cat_id": [
    "Этот котик уже добавлен в подборку."
  ]
}
```

Ответ: `400 Bad Request`.

### Пример ошибки прав доступа

Если читатель пытается пригласить участника, API возвращает `403 Forbidden`:

```json
{
  "detail": "У вас нет прав для управления участниками подборки."
}
```

# Глава 3. Реализация проекта

Реализация расположена в приложении `backend/collaborations/`. Использован
> `ModelViewSet` для ресурса подборок и custom actions для управления
> участниками и составом котиков. Сериализаторы создают запись владельца
> атомарно, permission-классы разделяют доступ участника, владельца и редактора,
> а миграция `0001_initial` создаёт необходимые связи и ограничения. Выполнены
> `manage.py check`, `makemigrations --check --dry-run` и 38 тестов модулей
> `cats` и `collaborations` — все успешно. Docker Compose, PostgreSQL и внешний
> деплой в рамках этой проверки не запускались.

Для диаграммы Deployment будут отражены: клиент, Nginx, Django/DRF, PostgreSQL,
